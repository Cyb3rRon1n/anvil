# CLAUDE.md

Design notes for Anvil. A real, working build now exists (`installer/`, `templates/`, `tests/`) - detect → recommend → generate → optional start, with a CLI and bash+whiptail menu over the same engine. Everything below the "v0.1: first real build" section is either implemented-and-verified or explicitly marked as still open; treat anything not marked that way as current. Earlier design-stage sections are kept for the reasoning they carry, not as a claim that they're still unimplemented.

## Origin

Scoped out during a Vulcan session where the user asked whether Vulcan should grow "build type" selection (Media Server vs. Creativity) to cover local LLMs, ComfyUI, and Stable Diffusion alongside Jellyfin/*arr. The recommendation was to keep Vulcan narrow and spin this out as its own project instead — captured here so the idea isn't lost, not because the idea was bad.

## Why this can't just be a Vulcan mode

- **Different sizing axis entirely.** Vulcan's `TierDefinition` scores on CPU cores, RAM, and disk — right for a media stack, meaningless for GPU-compute workloads. A 7B-parameter LLM needs roughly 8GB of VRAM; a 70B needs 40GB+; none of that has anything to do with system RAM or CPU core count. Anvil's tiers would need to score primarily on **GPU VRAM** (and probably vendor/compute-capability), a dimension Vulcan's tier model has no hook for at all.
- **Vulcan's GPU detection was never built for this.** `detect_gpu()` (Vulcan's `installer/detect.py`) only checks vendor presence via `nvidia-smi`/`rocm-smi`/an `lspci` string match — confirmed by reading it, not assumed. It has never needed to know *how much* VRAM exists, because Jellyfin's hardware transcoding doesn't care. Anvil's whole tier model depends on that number.
- **A different category of real quirks.** Vulcan's "one hand-written compose block per service, because each carries small real quirks" convention exists because that's genuinely cheaper than a generic renderer for 17 services with real per-service gotchas. Anvil's services would carry a different set of real gotchas — model download/storage management (Ollama pulls models via its own mechanism; ComfyUI/A1111 typically expect models placed manually), CUDA/ROCm toolkit prerequisites (Vulcan already documents `nvidia-container-toolkit` as a real, currently-unsolved gap for its own *optional* NVIDIA transcoding path — for Anvil, GPU compute isn't optional, it's the entire point, so this gap can't be left unsolved the way Vulcan leaves it). That's a second full set of real-infrastructure verification work, not an extension of Vulcan's existing set.
- **Different storage assumptions.** Model files run 4GB–140GB+ each. Vulcan's hardlink-safe `${MEDIA_PATH}:/data` volume convention (built around a media library's directory shape: movies/tv/music/books) doesn't map cleanly onto "where do multi-gigabyte model weights live and how do multiple services share them without duplicating downloads."

## What genuinely carries over from Vulcan's architecture

Not the tier model or GPU detection — the *pattern* around them, which is domain-agnostic and already proven:

- **Detect → recommend → generate**, the same three-stage shape Vulcan's `detect.py` → `tiers.py` → `generate.py` already establish.
- **Pure manager functions, never raising** — every real operation returns a plain result dict (`{"success"/"available": bool, "error": str | None, ...}`), the CLI layer alone owns confirmation prompts and stdout/stderr. Vulcan's engine/front-end split (`installer/` engine modules stay prompt-free; `cli.py` + `menu.sh` own all interaction) is worth copying exactly.
- **CLI + whiptail menu over one engine** — a Typer CLI (`--plain`/`--non-interactive` for direct prompts) plus a bash+whiptail main menu (`menu.sh`), neither owning logic the other lacks. The default `anvil` invocation launches the whiptail menu; `--plain` goes straight to the CLI's interactive prompts.
- **Docker Compose generation via Jinja, one block per known service** — not a generic data-driven renderer. Vulcan's own documented reasoning for this (real per-service quirks are easier to read and maintain as literal, mostly-static template blocks) likely holds here too, once the real service list and their real quirks are known.
- **Real-infrastructure verification as a non-negotiable project value, not optional polish.** Every Vulcan feature in this workspace ships with a "verified against a real container/real hardware" step, and claims are written to reflect exactly what was and wasn't checked. Anvil should hold itself to the identical bar — a `nvidia-smi`-based VRAM check that's never been run against a real GPU is exactly the kind of unverified claim Vulcan's own CLAUDE.md is careful never to make.
- **No LLM in the sizing decision path**, ironic as that sounds for a project that deploys LLMs — Vulcan's "deterministic, not AI-driven" tier scoring is a real design principle (reproducible, explainable, no hidden model behavior in *how a recommendation gets made*), and there's no reason Anvil's own tier math shouldn't be equally deterministic even though the workload it's sizing for happens to be AI.

## v0.1: first real build

Real Python package now exists (`pyproject.toml`, `installer/detect.py`/`tiers.py`/`generate.py`/`cli.py`, `templates/docker-compose.yml.j2`, `tests/`), following Vulcan's engine/CLI split exactly. `anvil` entry point mirrors `vulcan`'s shape: `--non-interactive`/`--yes`, real detection printed up front, tier confirm, generate, optional `--start`.

**Service list and pairing researched from real, current community sources, not picked from the README's original unverified placeholder list.** Searched what self-hosters are actually running together in 2026 (multiple independent write-ups, not one source) rather than assuming the original candidate list was right:

- **Ollama + Open WebUI is the standard, near-universal pairing** — Ollama as the model runtime (OpenAI-compatible REST API), Open WebUI as the chat frontend. Confirmed as the "starter stack" across every source checked.
- **ComfyUI integrates with Open WebUI for inline image generation** — a real, established pattern, not speculative. Confirmed the *exact* mechanism via Open WebUI's own docs: it's a **runtime admin-panel configuration** (Admin Panel > Settings > Images > enable Image Generation > engine = ComfyUI > point at the endpoint > Verify Connection), not a docker-compose-level wiring — nothing to automate beyond generating both services on the same network and telling the user where to click, so `write_stack()` does exactly that (mirrors Vulcan's Uptime Kuma "visit X, do Y" reference pattern precisely).
- **Stable Diffusion WebUI/AUTOMATIC1111 dropped from the v0.1 list** — every current source treats ComfyUI as the more actively-developed, more capable option; A1111 shows up only as "more turnkey but less capable." Not implemented for v0.1 to keep the service count tight; can be added later as a real alternative once the same rigor is applied to it.
- **Real, commonly-cited VRAM thresholds became the tier boundaries**: "8GB+ VRAM unlocks 14B models and usable image generation," "12GB+ (RTX 3060 12GB specifically named) is the real sweet spot" — both cited independently across sources, not from one write-up. Mapped onto Vulcan's own Light/Medium/Heavy naming for cross-project consistency: Light = any real VRAM below 8GB (small/quantized models only), Medium = 8GB+ (comfortable up to ~14B), Heavy = 12GB+ (adds ComfyUI).

**Real per-service integration facts, verified against official docs/repos before writing the template, not guessed:**

- **Ollama**: `ollama/ollama:latest` (NVIDIA/CPU) vs. `ollama/ollama:rocm` (AMD) — a real, separate tag, not an env var switch (confirmed via Docker Hub). Port `11434`, models at `/root/.ollama`. NVIDIA GPU access via compose's `deploy.resources.reservations.devices` (`driver: nvidia`, `capabilities: [gpu]`); AMD via `/dev/kfd` + `/dev/dri` device passthrough (the same `/dev/dri` mechanism Vulcan already uses for Jellyfin's AMD/Intel transcoding, plus `/dev/kfd` for ROCm compute specifically) and the host's render-group gid (`detect_render_group_gid()`, copied verbatim from Vulcan's `detect.py` — a genuinely reusable, domain-agnostic host-detection concern, not GPU-VRAM-specific).
- **Open WebUI**: `ghcr.io/open-webui/open-webui:main`, internal port 8080 (published as 3000, matching the convention most guides use), `OLLAMA_BASE_URL=http://ollama:11434` — plain container-to-container DNS over the compose network, no extra wiring.
- **ComfyUI has no single official/canonical image, confirmed by checking** — unlike Ollama and Open WebUI, ComfyUI's own project ships no Docker image; the ecosystem is community-maintained. Picked `mmartial/comfyui-nvidia-docker` (explicit UID/GID configurability matching this project's PUID/PGID convention, actively maintained) after confirming it's real and published (`docker manifest inspect`) and reading its actual real docs for exact volume/port/env shape (`/comfy/mnt` for the runtime, `/basedir` for models/input/output/user data, port 8188, `WANTED_UID`/`WANTED_GID`/`BASE_DIRECTORY`/`SECURITY_LEVEL`). **This image is NVIDIA-only, confirmed via its own docs (no ROCm/AMD mention, explicitly CUDA-only)** — `tiers.py`'s `ServiceDefinition(vendor_restriction="nvidia")` gates it out for AMD/Intel hosts, and `write_stack()` emits a clear warning naming the real reason (not a silent drop) rather than pretending the vendor gate doesn't exist. A ROCm/Intel-compatible ComfyUI image is a real, still-open gap, not solved here.

**Real bugs found only by testing, not by reading the code back:**

- **The CLI's own `--start` never actually ran** — `python -m installer.cli` produced zero output and exit code 0 regardless of arguments, because the module never called `app()` — missing the `if __name__ == "__main__": app()` guard Vulcan's `cli.py` has at the bottom. Invisible via `CliRunner`-based testing (which calls `app` directly, not the module), only caught by literally running `python -m installer.cli` for real and noticing nothing happened.
- **`comfyui_default` defaulted to `True` regardless of GPU vendor** — a fresh, non-interactive run on real AMD/Intel hardware silently *requested* ComfyUI (`config.enabled_optional` contained `"comfyui"`) even though it could never actually render, relying entirely on `write_stack()`'s vendor gate to quietly drop it. Not wrong in its externally-observable effect (the warning still fired, the service still didn't render) but dishonest at the point closest to the user's actual choice - caught by a test (`test_non_interactive_heavy_amd_defaults_comfyui_off`) that initially failed for the right reason. Fixed: `comfyui_default` itself now checks `gpu.vendor == "nvidia"` before defaulting true, both in the interactive confirm's displayed default and the non-interactive silent value.
- **A real, direct confirmation of the exact false-positive class documented above** (Vulcan's `rocm-smi`-presence bug): running `detect_system()` for real on this machine returns `gpus=[]` — correctly empty, since this machine has no discrete GPU at all, only an Intel iGPU. No false "amd" the way Vulcan's own `detect_gpu()` reports on this identical machine. Direct, live proof the functional-query design decision works as intended, not just an assumption written into the docstring.
- **Test-pollution via a stray real `stack/` directory** — the exact same class of bug Vulcan's own history hit repeatedly (documented in its own CLAUDE.md multiple times), independently rediscovered here: an early manual verification run left a real `stack/.anvil-state.json` on disk, and a CLI test that didn't mock `installer.cli.STACK_DIR` silently picked up that stale state instead of the test's own fixture data, producing a confusing failure that looked like a tier-recommendation bug. Root-caused, the stray directory removed, and every CLI test that reaches `_gather`-equivalent logic now explicitly patches `STACK_DIR` to a `tmp_path`, matching Vulcan's own established test discipline exactly.

**Verified against real infrastructure, not just `docker compose config`:**

- Real `docker compose config` validation of a generated Heavy-tier NVIDIA stack (Ollama + Open WebUI + ComfyUI) — exit 0, all three services present with correct GPU reservation blocks, no warnings.
- **Real containers, real network, real API calls** — this machine has no discrete GPU to test ComfyUI against, but Ollama and Open WebUI needed none: started both for real (a scratch Docker network, since this machine already runs a real native `ollama` systemd service bound to the standard port 11434 - a genuine, useful finding in its own right, confirmed via `ps`/`ss`, and left completely untouched rather than stopped for convenience). Confirmed Ollama's real API responded (`{"version":"0.32.5"}`), confirmed Open WebUI came up healthy and served real HTML (`200`), and confirmed via `docker exec` that Open WebUI's container could reach Ollama's real API through the exact `OLLAMA_BASE_URL=http://ollama:11434` mechanism the generated compose file uses - not mocked, an actual container-to-container round trip.
- ComfyUI itself remains genuinely unverified (no NVIDIA hardware anywhere in this environment) - stated honestly, not implied otherwise.

## v0.2: GPU passthrough toolkit warnings + Textual TUI (removed in v0.12)

**GPU passthrough toolkit warnings** — `write_stack()` warned about ComfyUI's NVIDIA-only image constraint but said nothing about the NVIDIA Container Toolkit itself - a host can pass `nvidia-smi` detection cleanly (proving the driver works) while still lacking the separate OCI runtime hook Docker needs to actually pass a GPU into a container, and the generated stack would just fail to start with an opaque error. Added a warning (mirroring Vulcan's identical NVIDIA-transcoding caveat, real install-guide URL) whenever an NVIDIA GPU is detected and any service is enabled. **Deliberately no equivalent AMD/Intel warning** - confirmed by re-reading `detect_amd_gpus()`/`detect_intel_gpus()`: both only ever report a GPU when the real kernel driver (amdgpu, or Intel's discrete-GPU driver stack) is already loaded, since that's the same mechanism they read VRAM through - unlike `nvidia-smi`, which works standalone regardless of whether the separate NVIDIA Container Toolkit exists. Warning a user to "install a driver" detection has already proven is present would have been actively wrong, not just unnecessary.

**Textual TUI (`installer/tui/`)** was built in this slice and verified for real, but was superseded by the bash+whiptail menu (`installer/menu.sh`) in v0.12. The TUI code, its test suite (`tests/test_tui.py`), and the `textual` dependency have all been removed. The `--plain` flag now goes to the CLI's typer prompts directly, not the TUI.

## v0.3: real AMD ComfyUI support

**Closed the single biggest real gap from v0.1/v0.2** - AMD Heavy-tier users previously got zero image-generation capability at all, only a warning. Researched real, current AMD ROCm ComfyUI options rather than assuming none existed:

- **AMD's own official image (`rocm/comfyui:comfyui-0.18.2.amd0_rocm7.2.0_ubuntu24.04`) targets data-center Instinct GPUs (MI355X/MI325X/MI300X) specifically, confirmed via AMD's own ROCm docs** - not what a homelab user has. Consumer Radeon support needed a community image instead.
- **Picked `corundex/comfyui-rocm`, confirmed real via `docker manifest inspect` and its own real README** - explicitly targets "AMD RX 6000/7000+ series," the right scope for this project (consumer hardware, matching who's actually running this). Real, verified shape: port `8188`, `/dev/kfd` + `/dev/dri` device passthrough + `video` group (the exact same mechanism already built for Ollama's AMD path - `detect_render_group_gid()`, reused unchanged, no new code), volumes at `/workspace/ComfyUI/{models,output,input,custom_nodes,user}` (a genuinely different path convention from the NVIDIA image's `/basedir/models` - both wired into their own vendor-specific compose block, and both surfaced correctly in the CLI's "where do checkpoints go" copy, which is now vendor-aware instead of hardcoding the NVIDIA path).
- **`ServiceDefinition.vendor_restriction: str | None` became `vendor_restrictions: frozenset[str] | None`** - the moment a second vendor needed support, a single-string field stopped being enough; `enabled_service_keys()`'s gate changed from `!=` to `not in`. Small, mechanical, but a real design point shared with this whole workspace: generalize once a second real case actually forces it, not preemptively for a case that might never come.
- **Intel Arc remains genuinely unsupported** - no ComfyUI image research has been done for it, and `comfyui_supported` (`cli.py`/`config_screen.py`) and `vendor_restrictions` (`tiers.py`) both explicitly only allow `{"nvidia", "amd"}`. The warning text (`generate.py`) was updated to reflect two real supported vendors and one real gap, not three unknowns.
- **Verified**: `docker compose config` against a real generated AMD Heavy-tier ComfyUI stack - valid syntax, correct `/dev/kfd`/`/dev/dri` device entries, correct `group_add`, correct image. **Not verified**: no real AMD GPU exists in this project's environment (same honest limitation as NVIDIA ComfyUI before it) - stated plainly, not implied otherwise.

## v0.4: real Intel Arc ComfyUI support - the last vendor gap closed

**All three real vendors `detect.py` can detect (NVIDIA, AMD, Intel Arc) now have a real, verified ComfyUI image.** Researched real options rather than assuming Intel Arc had none - it turned out to be the best-covered of the three, several actively-maintained multi-vendor projects exist (`joepitt91/comfyui-docker`, `reliq-hq/docker-comfyui`, `YanWenKun/ComfyUI-Docker`, the last of which already supplied the AMD ROCm research in v0.3 too).

- **Picked `yanwk/comfyui-boot:xpu`, confirmed real via `docker manifest inspect` (a real multi-arch manifest list) and its own real repo docs** - explicitly supports Arc Alchemist (A-series: A770/A750/A580 and mobile variants) and Arc Battlemage (B-series: B580/B570/B70/B60/B50), matching exactly the same discrete-only hardware class `detect_intel_gpus()` already targets via `xpu-smi`.
- **A real, structural difference from the NVIDIA/AMD images, found by reading the real docs, not assumed**: this image runs as root internally with no PUID/PGID equivalent at all ("No UID/GID variables: None specified" in its own docs) - unlike `mmartial/comfyui-nvidia-docker` (`WANTED_UID`/`WANTED_GID`) or even AMD's `corundex/comfyui-rocm` (which needs `group_add` for its non-root process to reach `/dev/dri`). Running as root sidesteps the Linux device-group-permission problem entirely, so **no `group_add`/render-gid is needed for the Intel block** - confirmed correct by reasoning about *why* the AMD image needed it (non-root process, host device node owned by a group) rather than pattern-matching the AMD block blindly.
- **Two real, non-default flags the source docs explicitly required, both included rather than dropped as "probably optional"**: `ipc: host` (shared-memory performance, a real standard Compose top-level key) and `security_opt: [label=disable]` (an SELinux-labeling disable - matters on SELinux-enforcing hosts like Fedora/RHEL, this project's own real dev machine among them; a documented no-op on non-SELinux distros, not something that would break a Debian/Ubuntu host).
- **Volume paths land on `/root/ComfyUI/...`, genuinely different from both other vendors' paths** (`/basedir/models` for NVIDIA, `/workspace/ComfyUI/...` for AMD) - a third real, distinct convention, not a copy-paste of either. `cli.py`'s/`ConfigScreen`'s "where do checkpoints go" messaging already generalized to "NVIDIA gets `basedir/models`, everything else gets `models`" in the AMD slice, and that logic needed zero changes here - AMD and Intel happen to share the same *relative host path* (`stack/data/comfyui/models`) even though the *container-side* mount target differs, and the messaging only ever needed the host-side path anyway.
- **`vendor_restrictions` is now `frozenset({"nvidia", "amd", "intel"})`** - no further generalization needed, the `frozenset`-membership design from v0.3 already scales to a third vendor for free, exactly why it was changed from a single string then instead of waiting.
- **The `generate.py` "ComfyUI was requested but skipped" warning is now genuinely defensive, not a live code path** - reachable only if `config.gpu` is `None` (a real, if currently unreachable through normal `recommend_tier()` flow, edge case, still tested) or a future vendor gets VRAM detection before a matching image is researched. Kept rather than deleted, since `GenerationConfig` can be constructed directly (tests already do this), not only through the CLI's own gating.
- **Verified**: `docker compose config` against a real generated Intel Heavy-tier ComfyUI stack - valid syntax, correct `/dev/dri`, `ipc: host`, and `security_opt` entries, correct image, no spurious `group_add`. **Not verified**: no real Intel Arc discrete GPU exists in this project's environment (same honest limitation already stated for NVIDIA and AMD) - all three vendors' ComfyUI images are real and syntactically correct, none has been started against real matching hardware yet.

## v0.5: model-storage strategy investigated for real - port-conflict detection instead of directory sharing

The roadmap's "model storage strategy" item assumed the open question was *sharing* model downloads across services. Investigated for real rather than assumed, and the premise turned out to be half wrong:

- **Ollama and ComfyUI never share a downloadable file, so there's nothing to dedupe between them.** Ollama serves GGUF-quantized LLMs through its own content-addressed blob store (`manifests`/`blobs`, not plain named files); ComfyUI loads diffusion checkpoints (`.safetensors`/`.ckpt`) for image generation. Different formats, different domains, zero real overlap - "avoid downloading the same model twice for two different tools that both want it" was never a real scenario for this stack's actual service set. This half of the original roadmap item is closed, not deferred.
- **The real duplicate-download risk is narrower and more concrete: a host that already runs Ollama natively.** Verified on this project's own real dev machine, not hypothetical - a genuine `ollama.service` (systemd, `0.32.5`) was found running, already holding a real 4.9GB `llama3.1:latest` model. A fresh `anvil` run on a host like this would silently try to start a second Ollama on the same port and, if that were somehow worked around, redownload everything the native install already has.
- **Directory-sharing was considered and rejected for a real, verified reason, not skipped for convenience.** The native install's model store lives at `/usr/share/ollama/.ollama`, owned by a dedicated `ollama` system user with the directory itself locked to mode `0700` - confirmed directly on this machine (`stat`/`ls` both refused with `Permission denied` as the invoking user, before even reaching the `models` subdirectory). Reusing it would require either loosening those permissions or running Anvil's container as that system UID - both real operational asks for what's supposed to be a lightweight install helper, and mounting the same blob store into two independently-running Ollama servers (native + containerized) simultaneously risks concurrent-write corruption of the manifest store regardless. Not attempted.
- **What shipped instead: honest conflict detection.** `detect.py` gained `port_in_use(port, host="127.0.0.1")` - a real TCP `connect_ex` probe, never a `ps`/`ss` shell-out, so it works the same regardless of what's listening. `generate.py`'s `write_stack()` checks it for every enabled service's published port (`SERVICE_PORTS = {"ollama": 11434, "open-webui": 3000, "comfyui": 8188}`) and appends a warning through the same `warnings` list every other real-condition warning already flows through (NVIDIA Container Toolkit, Open WebUI/ComfyUI wiring) - no new display plumbing needed in the CLI or `ReviewScreen`, both already print `result["warnings"]` verbatim. Ollama's warning is deliberately richer than a generic "port taken" message - it names the likely cause (`systemctl status ollama`), the fix (`sudo systemctl stop ollama`), and the honest cost of that fix (models redownload into this stack's own `data/ollama`) - matching this project's explainability standard, not just "port busy."
- **Verified end-to-end against this exact real conflict**: a real `write_stack()` call against this dev machine's genuine bound port 11434 produced the correct Ollama-specific warning text, not a mock.
- Five new tests: two real (unmocked) socket tests for `port_in_use()` in `tests/test_detect.py` (bind-and-listen on an OS-assigned ephemeral port confirms `True`; bind-then-close confirms `False` for the same now-free port, rather than guessing a literal), three in `tests/test_generate.py` covering the Ollama-specific message, the generic per-service message, and the no-conflict case.
- **Real test-pollution bug caught immediately by running the suite, not anticipated in advance**: `port_in_use()` doing a real network probe meant every *existing* `write_stack()` test in `tests/test_generate.py` started hitting this machine's real bound port 11434 too, breaking an unrelated assertion (`test_write_stack_no_gpu_produces_no_toolkit_warning` expected `warnings == []`) - the same class of ambient-state leak already seen once before with the stray `.anvil-state.json` file. Fixed with an autouse `no_real_port_conflicts` fixture in `test_generate.py` that patches `port_in_use` to `False` by default; the handful of tests that actually exercise conflict behavior override it with their own nested `patch()`.

## v0.6: real model-capability verification, correcting an unverified tier claim

The "8GB+ comfortable up to ~14B models" claim baked into the tiers since v0.1 came from commonly-cited community write-ups, explicitly flagged in this file as "not independently verified against a real model load yet." Verified for real this slice, against harder evidence than another round of community blog posts.

- **Real, hard numbers pulled from Ollama's own published library, not community estimates**: `llama3.1:8b-instruct-q4_K_M` is a real 4.9GB download; `qwen2.5:14b-instruct-q4_K_M` is a real 9.0GB download (both fetched directly from `ollama.com/library`). GGUF model weights load into VRAM at close to their on-disk size, so these are close to the real floor a card needs before context/KV-cache overhead is even added.
- **The real math contradicts the original claim.** A 9.0GB model on an 8GB card doesn't fit at all before context is even considered, let alone "comfortably." The rule-of-thumb overhead multiplier commonly cited alongside these figures (roughly +20% for modest context) puts a real comfortable floor for 14B-class models around 11GB - past Medium's 8GB threshold, safely inside Heavy's 12GB one. 7-9B-class models (Llama 3.1 8B's real 4.9GB) do genuinely fit 8GB comfortably, matching Medium's original intent for that model class.
- **Cross-checked against real SDXL/ComfyUI guidance too, not just LLMs**: 12GB is repeatedly and independently cited as the real recommended floor for a full SDXL + refiner pipeline (8GB "works," 12GB is the actual comfort line) - corroborates Heavy's existing 12GB threshold as the right line for adding ComfyUI, not just a round number.
- **The fix was to the *claim*, not the *thresholds*.** 8GB and 12GB as the Medium/Heavy cutoffs both held up under real numbers - what was wrong was describing Medium as good for "up to ~14B." `TierDefinition` gained a new required field, `capability_note`, holding an accurate, cited one-line description per tier (Light: small quantized models only; Medium: comfortable 7-9B, 14B fits VRAM-wise but tight; Heavy: comfortable 14B, plus the real SDXL sweet spot) - `tiers.py`'s module docstring documents the correction and its math directly rather than only living in this section.
- **This closes a real "the docs said something nobody had checked" gap, the same class of finding as the Intel/AMD image research** (verify what's actually true before shipping it as guidance), not a new kind of bug for this project.
- **Wired into every place a tier is shown, not just left as an unused field**: the CLI's review step, summary text, and - net new, not just a docs fix - real `tooltip=` hints on each tier's `RadioButton` in the whiptail tier picker, the same established pattern already used for the ComfyUI checkbox and PUID/PGID inputs. Previously the tier picker showed only bare "Light"/"Medium"/"Heavy" labels with zero indication of what any of them actually got you - closing that gap was as real a fix here as correcting the wrong number, given this project's explicit "user-friendly" mandate.
- Four new tests: three in `tests/test_tiers.py` (every tier has a real non-empty note; a regression lock that Medium's note no longer claims 14B comfort; Heavy's does). Full suite: 67 passed.

## v0.7: a landing page and the real AMD ComfyUI-Manager gap

Two companion features, scoped together from a user question about what else a "creative suite" setup needs beyond the three core services.

**ComfyUI-Manager - a real, vendor-specific gap, found by reading each image's own docs, not assumed.** ComfyUI itself ships no manager of any kind; the near-universal community answer is the separate `ComfyUI-Manager` custom node (github.com/Comfy-Org/ComfyUI-Manager - confirmed current, `ltdrdata/ComfyUI-Manager` resolves to the identical commit, ownership moved to the Comfy-Org). NVIDIA's (`mmartial/comfyui-nvidia-docker`) and Intel's (`yanwk/comfyui-boot:xpu`) images both already bundle it, confirmed via their own docs. AMD's (`corundex/comfyui-rocm`) doesn't - confirmed by reading its README directly, no mention of it anywhere. **Not auto-installed, for a real reason found by reading the AMD image's actual `startup.sh`, not assumed:** it runs `python main.py` directly with no step that installs a custom node's own `requirements.txt` - a bare `git clone` into the `custom_nodes` volume alone would very likely leave Manager present but broken (import failure from missing dependencies) on first boot. Fixing that properly would mean either overriding the base image's own startup behavior (fragile across image updates) or giving `write_stack()` a new `git` + network dependency it's never had before, for a payoff that still needs a `pip install` step to run *inside* the container after it exists anyway. `write_stack()` instead detects AMD+ComfyUI and warns with the exact three real commands to run once after first start (`git clone` into the host-side custom_nodes path, `docker compose exec comfyui pip install -r .../requirements.txt`, `docker compose restart comfyui`) - same "explain rather than silently automate something fragile" precedent as the NVIDIA Container Toolkit warning.

**Dashboard - a lightweight static landing page, not Vulcan's full Homepage container.** Considered porting Vulcan's `gethomepage.dev` integration directly, but that's a real dashboard framework (backend, service monitoring, icon/config parsing) sized for Vulcan's up-to-17-service stack; Anvil tops out at 3. Went with a minimal generated `dashboard/index.html` (new `templates/dashboard.html.j2`, rendered by a new `render_dashboard()` in `generate.py`) served by a plain `nginx:alpine` container on port `8080` - near-zero resource cost, no new Python dependency, one Jinja template instead of a second integration to maintain. Unconditionally rendered every tier (not a `tiers.py` `ServiceDefinition` - it's not user-choosable or vendor-gated the way the real services are, so it deliberately sits outside `enabled_service_keys()`), regenerated on every `write_stack()` call rather than write-once-never-overwrite like Vulcan's `services.yaml` - there's nothing user-editable in it to protect, unlike a real dashboard app's config.

**`detect_host_ip()` ported from Vulcan verbatim, not reinvented** - a hardcoded `localhost` in the generated HTML would be wrong the moment the dashboard is opened from a different device than the one running the stack, the common case for a homelab GPU box. Same real technique Vulcan already proved: a UDP "connect" to a public address sends no actual packets, it only asks the kernel's routing table which local address it would use - which is exactly the address other devices on the same LAN can reach this host at. Falls back to `localhost` if detection fails (e.g. no route out at all).

**Port conflict handling extended to the dashboard, using the port-conflict mechanism from v0.5 unchanged** - `DASHBOARD_PORT = 8080` gets its own `port_in_use()` check in `write_stack()` alongside the existing per-service loop (kept separate from `SERVICE_PORTS` since that dict is only ever walked over the `enabled` set, which the dashboard deliberately isn't part of). **This wasn't a hypothetical scenario written for coverage - port 8080 turned out to be genuinely bound on this exact dev machine** (confirmed via `ss -ltn`), so the new warning was verified against a real, live conflict, not just a mock, the same day it was written.

**Verified against real Docker, not just `docker compose config`:** generated a real Heavy-tier NVIDIA stack and confirmed `dashboard:` renders in every tier (light/medium/heavy) with the correct image/port; started the real `nginx:alpine` container (on a scratch host port, since 8080 was genuinely taken) against the actual generated `dashboard/index.html` and confirmed a real `200` response with the real page content, including the real detected LAN IP (`192.168.1.100` on this machine) in every link - not `localhost`. Confirmed the dashboard's links correctly track `enabled_service_keys()`: Light tier's page has no ComfyUI link, Heavy+ComfyUI's does.

## v0.8: InvokeAI, a second image-generation option

The roadmap's "a second image-generation option beyond ComfyUI" item, never scoped before this. Researched real, current (2026) alternatives rather than defaulting to the one everyone already knows (A1111) - the landscape turned out to be more fragmented than expected, worth working through explicitly rather than picking the first name that came up.

**Real research, not a single source.** A1111 (`AUTOMATIC1111/stable-diffusion-webui`) - development effectively stalled, last major release mid-2024, can't run Flux, only minor maintenance since. The original Forge (`lllyasviel/stable-diffusion-webui-forge`) - maintainer inactive since November 2024, no fresh official release, though community PRs kept landing through mid-2025; community continuations (Forge Neo/Classic) picked up the slack instead. Fooocus (`lllyasviel/Fooocus`) - not archived, but its own README declares "limited long-term support (LTS), bug fixes only," no new architectures; a community fork (mashb1t's "1-Up Edition") is the active continuation, and neither the original nor the fork has an official multi-vendor Docker story (only third-party, cloud-rental-oriented images like AI-Dock's exist). **InvokeAI is the real standout**: actively maintained, and independently, repeatedly described across current comparisons as the actual "turnkey" choice next to ComfyUI - a unified canvas with layers/brush tools and a real built-in Model Manager, not a node graph, genuinely the better fit for "users who find ComfyUI's node-based UI too involved" (the roadmap item's own framing).

**The decisive factor for this project specifically: InvokeAI ships its own official multi-vendor Docker images, confirmed by fetching the real files, not a summarized version.** `invoke-ai/InvokeAI`'s own `docker/` directory has a real `docker-compose.yml`, `.env.sample`, `Dockerfile`, and `docker-entrypoint.sh` - fetched all four directly (`curl` on the raw GitHub content, not `WebFetch`'s AI-summarized version) after that summarized version turned out to describe `CONTAINER_UID` as build-time-only, which the real entrypoint script contradicts (see below). This project has been burned by trusting a summarized fetch over the real source exactly once already - Vulcan's Decluttarr slice, where a summarized doc fetch invented a `!ENV` config tag that didn't exist - so this was worth doing right the second time a real design decision hinged on exact file contents.

**Real image tags, confirmed via `docker manifest inspect`, not assumed from docs:** `ghcr.io/invoke-ai/invokeai:latest` (NVIDIA/CUDA, the default) and `ghcr.io/invoke-ai/invokeai:main-rocm` (AMD) - both real, both `amd64`/`linux`. No Intel Arc image exists at all - confirmed by searching specifically for it: only a non-Docker community repo (`Raasu2/invokeai-xpu`, explicitly "no Docker" in its own title) exists, with documented VRAM-detection issues on top. A real, currently-live gap, not a future-vendor hypothetical the way ComfyUI's equivalent already-closed gaps were - `vendor_restrictions=frozenset({"nvidia", "amd"})`, and both `write_stack()`'s "requested but skipped" warning and the CLI's support checks say so explicitly rather than silently omitting the checkbox with no explanation.

**A genuinely different AMD mechanism from every other AMD block in this project, found in the real fetched `docker-compose.yml`, not assumed to match the existing pattern.** Ollama's and ComfyUI's AMD images both use plain `/dev/kfd` + `/dev/dri` device passthrough plus `group_add` at the host's render gid - no special Docker runtime required. InvokeAI's real official AMD service instead specifies `runtime: amd` (AMD's own separately-registered Container Runtime Toolkit, installed and configured via `amd-ctk runtime configure`, which writes an `"amd"` entry into `/etc/docker/daemon.json`) plus `AMD_VISIBLE_DEVICES=all` and `RENDER_GROUP_ID` (still `detect_render_group_gid()`, reused unchanged - only the *mechanism* around it differs, not the gid source). This is a real, separate host prerequisite Anvil's other AMD services never needed - closing the gap the same way the existing NVIDIA Container Toolkit warning already does: a new warning fires whenever InvokeAI+AMD is enabled, naming the toolkit and linking `instinct.docs.amd.com`'s real install guide, since detecting the GPU (`detect_amd_gpus()`) proves nothing about whether this separate runtime is registered.

**`CONTAINER_UID` is real and runtime-configurable - confirmed by reading the actual `docker-entrypoint.sh`, not the Dockerfile alone.** The Dockerfile's `CONTAINER_UID`/`CONTAINER_GID` `ARG`s looked like build-time-only settings at first (an AI-summarized fetch of the docs page said as much), but the real entrypoint script reads `CONTAINER_UID` from the environment at container start and applies it via `usermod -u` + `gosu`, the same LinuxServer-style runtime-UID pattern this project's own PUID convention already expects. **A real, worth-documenting asymmetry: there is no equivalent runtime GID knob.** The entrypoint never touches group membership for the primary user beyond what the image was built with - `CONTAINER_GID` only exists as a Dockerfile `ARG` baked in at image-build time, invisible to a `docker run`/`docker compose up` against the pre-built published image. So the compose block passes `CONTAINER_UID={{ puid }}` only; `pgid` is silently inert for this one service, a genuine per-service quirk (matching this project's own "one hand-written block per service because each has real quirks" principle), not an oversight.

**Genuinely simpler for the user than ComfyUI, confirmed by reading InvokeAI's own docs, not assumed from "turnkey" branding alone.** InvokeAI has a real built-in Model Manager (a UI panel, not a separate tool) that downloads and registers checkpoints directly - paste a HuggingFace repo ID, or pick from a curated "Starter Models" list shown on first launch. This is materially different from ComfyUI's "place the file yourself" requirement, and it's why InvokeAI's own config-screen tooltip and CLI confirm prompt say "no manual file placement needed" instead of ComfyUI's "model checkpoints have to be placed manually under `<path>`" - a real behavioral difference reflected in the copy, not copy-pasted from the ComfyUI checkbox and re-labeled.

**Wired the same way ComfyUI already was, defaulting on for supported hardware - not a new pattern.** A 4th `ServiceDefinition("invokeai", ...)` at Heavy tier, `SERVICE_PORTS["invokeai"] = 9090`, a `--invokeai/--no-invokeai` CLI flag mirroring `--comfyui/--no-comfyui` exactly, an `invokeai-check` `Checkbox` in `ConfigScreen` visible only when `gpu.vendor in ("nvidia", "amd")` at Heavy tier, and the same "requested but skipped" defensive warning ComfyUI's equivalent already has - except InvokeAI's version is live, not defensive, on Intel Arc today. Both image-gen services can be enabled together; nothing about their compose blocks, ports (`8188` vs `9090`), or volumes (`data/comfyui/*` vs `data/invokeai`) conflicts.

**Verified past what `docker compose config` alone would show - the first time an image-generation service in this project has been started for real, even without matching GPU hardware.** Every prior ComfyUI vendor slice stopped at `docker compose config` syntax validation, honestly noting no discrete GPU exists in this environment to go further. For InvokeAI, went one step past that: pulled the real `ghcr.io/invoke-ai/invokeai:latest` image and started a real container with no GPU flags at all. It came up cleanly - logged `Using torch device: CPU` (a real, honest fallback, not a crash), ran its real SQLite migrations, and bound its web server (`Invoke running on http://0.0.0.0:9090`); a real `curl` against the published port answered `200`. Confirmed via `ls -lan` that its bind-mounted data directory was owned by the real passed-in `CONTAINER_UID` (`1000:1000`), not root - the runtime-UID mechanism described above genuinely took effect, not just present in the rendered compose file. Separately confirmed the AMD path's *documented failure mode* is real, not hypothetical: `docker run --runtime=amd ...` against this exact machine (which has no AMD Container Toolkit registered) failed with exactly `unknown or invalid runtime name: amd` - the precise scenario the new warning describes. What's still unverified, honestly: actual image generation against a real NVIDIA or AMD GPU - no discrete GPU of either vendor exists in this environment, the same limitation ComfyUI has always had.

## v0.9: Docker install-assist, including a real atomic/immutable-OS path

Direct fallout of trying Anvil for real against a real GPU host - `msi-laptop`, a Bazzite (Fedora Kinoite-based) laptop reached over Tailscale, with a real RTX 2080 (8GB VRAM, already confirmed working for Ollama inference in the sibling `oracle` project's own GPU migration). Anvil's own `_gather`-equivalent flow got to `docker_installed`/`docker_running`/`docker_compose_v2` and just printed `docs.docker.com` and exited - the exact "most people reaching for GPU-compute self-hosting already have Docker" assumption this project's own CLAUDE.md and ROADMAP.md previously named as a deliberate scope-down, contradicted by the first real host tried against it.

**Ported, not reinvented - `installer/docker_setup.py` is Vulcan's own already-real-verified module of the same name**, copied with its exact function shapes (`install_plan_for`/`install_docker`/`ensure_compose_v2`/`add_user_to_docker_group`/`start_docker_service`/`run_docker_command`) and the same `shell.py` (`run_ok`/`run_privileged`) helpers Anvil already had sitting unused since v0.1. `get.docker.com` (ubuntu/debian/raspbian/fedora) and `pacman` (arch) needed no changes to work here - Vulcan's own CI-verified real-Docker test already covers that mechanism.

**The one genuinely new capability, not in Vulcan's version**: atomic/immutable hosts (Fedora Silverblue/Kinoite, Bazzite, other Universal Blue derivatives) can't `dnf install` anything - the base image is read-only, packages are *layered* via `rpm-ostree install` instead, and that layering only takes effect after a reboot. `detect.py` gained `detect_os_is_atomic()`, checking `/run/ostree-booted` (ostree's own real boot-time marker, confirmed present on the actual Bazzite host and absent on this project's own normal-Fedora dev machine - not a name guess) with `shutil.which("rpm-ostree")` as a narrower, unconfirmed-in-the-wild fallback. **`install_plan_for` checks `os_is_atomic` before `os_id`, not after** - a real, load-bearing ordering: Bazzite/Kinoite both report `os_id="fedora"` (`ID_LIKE=fedora` in `/etc/os-release`, confirmed by reading the real file over SSH), which would otherwise route straight into `DOCKER_SCRIPT_DISTROS`'s plain `curl | sh` script against a read-only root - wrong, not just suboptimal. The atomic path instead runs two privileged steps (`curl` the real `download.docker.com/linux/fedora/docker-ce.repo` into `/etc/yum.repos.d/`, then `rpm-ostree install docker-ce docker-ce-cli containerd.io docker-compose-plugin docker-buildx-plugin`) and reports `needs_reboot: True` only on a real success - a failed repo-add correctly stops before ever attempting the layer, and a failed layer correctly reports `needs_reboot: False` (nothing was actually staged for a reboot to pick up).

**The CLI stops cleanly and honestly on `needs_reboot`, rather than chaining into steps that can't work yet.** `_ensure_docker_ready()` prints real reboot instructions and exits 0 (not an error - the install itself succeeded, it just isn't finished). Neither `start_docker_service()` nor `add_user_to_docker_group()` is called in this branch - those need a binary that doesn't exist yet. A second `anvil` run after the real reboot picks up cleanly through the ordinary `elif not info.docker_running` branch already built for every other host.

**`group_just_added` (Vulcan's own mechanism, ported unchanged) closes a real same-run UX gap**: a user just added to the `docker` group has a stale cached group list in the same process, so a same-run `docker compose up` would otherwise fail with a permission error despite the fix having "worked." Both the CLI and `ReviewScreen._run_start()` now route the final start command through `run_docker_command(..., use_group_workaround=group_just_added)` - `sg docker -c "..."` re-reads group membership fresh from the system, no relogin needed, falling back to `sudo` if `sg` itself isn't present.

**Verified for real, end to end, against the exact host that exposed the gap - not honestly-bounded-but-incomplete, fully closed out.** The user ran the real flow against `msi-laptop` over several live passes, each one reported back and the code fixed against real output rather than guessed at:

1. **Fresh install**: `anvil --plain` detected Docker missing, offered the `rpm-ostree` plan, installed for real (a real repo add + a real 7-package layer - `docker-ce`, `containerd.io`, `docker-compose-plugin`, etc.), and exited cleanly with real reboot instructions. Confirmed correct on the first try.
2. **Real bug #1, found live**: `detect_disk()`'s default path (`"/"`) reported `Disk free: 0.0GB` right next to "model checkpoints commonly run 4-140GB+ each" - alarming, and wrong. Bazzite's `/` is a tiny, nearly-full composefs snapshot; the real ~820GB free lives wherever `stack/` actually gets written (wherever the tool is run from). Fixed by defaulting `detect_system()`'s `disk_path` to `"."` instead of `"/"` - correct on every host, not just atomic ones. Re-verified live: `818.75GB`, then `818.81GB` on the next pass.
3. **Post-reboot, first attempt**: Docker installed-but-not-running, correctly detected; `start_docker_service()` succeeded (`systemctl is-active docker` → `active`) - but the readiness re-check still failed with "Docker still isn't ready."
4. **Real bug #2, found live, the deeper one**: root-caused by hand over several live diagnostic round-trips with the user, not guessed. `/var/run/docker.sock` was `root:docker`, and `id sentinel` showed no `docker` group membership - but `add_user_to_docker_group()`'s `usermod -aG docker sentinel` had already run and reported success. Manually reproducing it live confirmed the real cause: **`usermod` reported exit 0 and silently wrote nothing**, because the `docker` group's canonical record was created by `systemd-sysusers` (visible in the original install's own log: `Running systemd-sysusers... done`) and lives only in `/usr/lib/group` - part of the read-only base image, resolved via `nsswitch.conf`'s `group: files [SUCCESS=merge] altfiles ...` line, never present in `/etc/group` (confirmed directly: `cat /etc/group` showed only `root`/`wheel`/`sentinel`, no `docker` entry at all). `gpasswd -a` was tried next and failed the same way, more honestly: `group 'docker' does not exist in /etc/group` - it, too, only ever looks at the literal file, never the NSS-merged view. **The real, live-tested fix**: manually running `echo "docker:x:958:" | sudo tee -a /etc/group` (958 being the group's real gid, from `getent group docker`) followed by `sudo gpasswd -a sentinel docker` worked - confirmed via `id sentinel` showing real `docker` membership, and a real `sg docker -c "docker info"` succeeding where it had failed moments before. This sequence is what `add_user_to_docker_group()` now does as a fallback: try plain `usermod` first (works on every non-atomic host, unchanged), verify with a real functional check (`_user_in_docker_group()`, `id -nG <user>` - never trust the tool's own claimed exit code, the same "functional check, not presence" principle this project's own GPU detection already lives by), and only fall back to the merge-entry trick if that check shows the plain path didn't actually work. Not gated behind `os_is_atomic` - the underlying cause (a group `usermod`/`gpasswd` can't see via plain file enumeration) is what matters, not the OS family name. `check_docker_ready(use_group_workaround=True)` (new) re-verifies `docker_running`/`docker_compose_v2` through the same `sg`-based workaround `run_docker_command()` already used only for the final start - needed because a plain re-check right after fixing group membership in the *same process* still inherits that process's own stale cached group list from login time, a second real gap the CLI's `_ensure_docker_ready()` and the TUI's `DockerReadyScreen` both had before this was caught.
5. **Third live pass, after both fixes**: `Docker is ready.` printed for real. Tier picker, PUID/PGID prompts, stack generation, and a real `docker compose up -d` all ran - real images pulled (`nginx:alpine`, `ollama/ollama:latest`, `ghcr.io/open-webui/open-webui:main`), a real network and containers created. It stopped only on a pre-existing, correctly-diagnosed, out-of-scope issue: port 11434 already bound by a **native** Ollama install on the same host (from `oracle`'s own earlier, unrelated GPU-migration work) - Anvil's own v0.5 port-conflict warning named the exact cause before the attempt, exactly as designed; Anvil just has no interactive remap/stop-and-retry the way Vulcan does (see "Still open," below - a separate, scoped gap, not part of this feature).

132 tests cover the logic, all passing both locally and re-run for real on `msi-laptop` itself: `tests/test_docker_setup.py` (ported from Vulcan's own suite, plus new atomic-specific cases for the repo-add-then-layer sequencing, `needs_reboot` correctness, and the full `usermod`-fails/`gpasswd`-fallback sequence including its own distinct failure modes - group truly missing, `usermod` itself failing with no fallback possible, the fallback's own `gpasswd` step failing, and `gpasswd` succeeding but the user still somehow not showing as a real member), `tests/test_cli.py` (declined/accepted/failed install at each of the three readiness gaps, the atomic reboot message, the group-workaround wiring into the final start command, and - closing a real coverage gap this live testing surfaced - `add_user_to_docker_group()`'s result now actually being checked instead of silently assumed to have worked).

**What's verified, and what isn't, stated plainly**: full unit-test coverage (`tests/test_tiers.py`, `tests/test_generate.py`, `tests/test_cli.py`, `tests/test_menu.bats` - 184 Python tests + 20 of 22 bats tests passing, the same 2 pre-existing bats failures this environment already had before this slice, confirmed via `git stash` before touching anything), a full-stack generation smoke-tested with every optional service enabled at once and the result parsed back through a real YAML parser (valid syntax, all 10 expected services present) - but **no Docker exists in the environment this slice was built in**, so unlike every prior vendor/image slice in this project's history, there was no `docker compose config` schema validation and no real container ever started against these five images. The image tags/env vars themselves come from ODS's own already-running production configs (not guessed), which is a real, if secondhand, source of confidence - but real `docker compose config` validation and a real container start (matching this project's own established bar for every service before it) are still open, tracked below rather than silently claimed.

## v0.14: Vulcan integration mode - a capability neither Anvil nor ODS had on its own

Direct follow-up to a question the v0.13/ODS research raised: ODS is a fully self-contained install (its own Caddy reverse proxy, its own mDNS hostnames, its own dashboard, its own port registry) with no notion of merging into an *existing* homelab at all - checked directly, not assumed. "Detect a co-located Vulcan stack, cross-check its real ports, add a section to its Homepage dashboard" is a genuinely new capability, not a port of anything ODS does.

**New `installer/vulcan_integration.py`, a leaf module** - takes plain data (`enabled`/`ports` sets and dicts) rather than a `GenerationConfig`, specifically so it never has to import `generate.py`/`tiers.py` and create a circular import (`generate.py` imports from it, not the reverse). Every function is a pure, non-prompting engine function, same split as every other module here - detection-and-confirm stays a CLI/menu-layer concern.

**Real positive identification, not a name/file-shape guess**: `find_vulcan_stack()` only counts a directory as a real Vulcan stack if it holds Vulcan's own `.vulcan-state.json` (written by Vulcan's own `generate.py:save_state()`) - some other project's `docker-compose.yml` lying around must never be mistaken for Vulcan's. Default search path is a sibling `vulcan/` directory relative to the current working directory, matching this exact multi-repo workspace's own real layout (`anvil/` and `vulcan/` as sibling checkouts under one root, confirmed via `my-repos/AGENTS.md`) - overridable via `search_paths` for any other layout.

**A real gap a live-only port probe can't catch, closed with a static cross-reference**: `detect.py`'s existing `port_in_use()` (used everywhere else in this project) only ever sees what's bound *right now* - it can't catch "Vulcan is stopped, Anvil generates first, both are configured for the same port, and they're guaranteed to collide the moment both are ever started together." `check_vulcan_port_conflicts()` instead reads Vulcan's own *real, already-rendered* `docker-compose.yml` back (`parse_compose_ports()`) - the one honest source, since a static port table (like this project's own `SERVICE_PORTS`) can drift from real remaps Vulcan's own conflict-remediation may have already applied.

**Homepage merge respects Vulcan's own write-once rule exactly, by owning exactly one named group.** Vulcan's `generate.py` never overwrites `services.yaml` once it exists, specifically so a user's own edits stay safe (see Vulcan's `CLAUDE.md`). `merge_into_vulcan_homepage()` honors that by touching only its own group (`"Creative Suite (Anvil)"`) and leaving every other group in the file completely alone - confirmed for real, not just by reading the code (see "Verified for real," below). Unlike Vulcan's own write-once rule, this one group *is* replaced on every call, not write-once - nothing in it is ever user-hand-edited (only Anvil's own tiles ever live there), so a rerun with a different enabled-service set updates the tile list instead of going stale. Inserted immediately before Vulcan's own `"Guides"` group (always last in Vulcan's `render_homepage_services()`), matching where a human editing the file by hand would place it.

**A genuinely new blast-radius category for this project - the only place Anvil has ever written outside its own `stack/` output** - stays a real, visible confirm rather than a silent default-on, even though the write itself is additive and safe. `cli.py`'s `run_install()` calls `find_vulcan_stack()` unconditionally; when nothing is found, `vulcan_stack_dir` stays `None` completely silently - no prompt, no flag, no behavior change from before this feature existed, satisfying the standalone-by-default requirement directly. When something *is* found: a real `typer.confirm()` in interactive mode, `--integrate-vulcan`/`--no-integrate-vulcan` for non-interactive (defaults to `True` when found, matching the "found → safe additive action → default on" pattern already established for RAG/voice/n8n in v0.13). `menu.sh` mirrors this exactly via two new fields on the existing `anvil detect` KEY=VALUE output (`VULCAN_STACK_FOUND`/`VULCAN_STACK_PATH`) - no detection logic duplicated in bash, the same rule the rest of this file already follows - with a `--yesno` confirm step that only appears in the step count/flow at all when a stack was actually found.

**Verified for real against a genuinely generated Vulcan stack, not synthetic fixtures** - Vulcan is a sibling repo in this exact workspace, so its own `installer.generate.write_stack()` was called directly (Docker/sudo aren't available in this build environment, the same limitation `docker_setup.py`-gated CLI paths hit - called the engine function directly instead, same technique used throughout this project's own test suite) to produce a real light-tier stack with Homepage enabled. **This surfaced a real, live port collision the first time it was tested, not a contrived example**: Anvil's `open-webui` and Vulcan's `homepage` both default to port 3000 - `check_vulcan_port_conflicts()` caught it correctly against the real generated compose file. The merge itself was confirmed against the real resulting `services.yaml`: Vulcan's own `Media`/`Media Management`/`Downloads` groups came through completely untouched, `"Creative Suite (Anvil)"` landed correctly ahead of `"Guides"`, and a second run with a different `enabled_optional` set replaced the group's tiles in place rather than duplicating it (confirmed by grepping the real file for a second `"Creative Suite"` occurrence - none found).

**Test coverage**: `tests/test_vulcan_integration.py` (13 tests, `installer/vulcan_integration.py` at 100% line coverage), new `generate.py`/`cli.py`/`menu.sh` integration tests covering the found-and-confirmed, found-and-declined, flag-override, and not-found paths. One real, live-caught test-pollution bug, the same class this project has hit before (the stray `.anvil-state.json`, the real bound port 11434): `find_vulcan_stack()`'s real default search path is a sibling `vulcan/` directory - exactly what this dev workspace has for real - so the *real* Vulcan stack generated to verify this feature was silently picked up by every unmocked CLI test, injecting an unexpected confirm prompt. Fixed with an autouse `no_real_vulcan_stack` fixture in `test_cli.py`, mirroring `test_generate.py`'s existing `no_real_port_conflicts` fixture exactly.

## Real open questions for whenever this starts for real

None of these have been researched yet — listed so they're not forgotten, not because they're answered — **except VRAM detection, below, which is now implemented and verified (see "v0.1: first real build" above).**

### VRAM detection mechanism — implemented in `installer/detect.py`

Findings below are verified commands/interfaces against official docs; the parsing logic for each is real, tested code (`tests/test_detect.py`), though only the AMD/no-GPU path has been confirmed against real hardware output (this machine's actual sysfs tree) - no NVIDIA/AMD/Intel Arc discrete GPU exists anywhere in this project's environment to verify real command output against.

**A real bug in Vulcan's own GPU detection, found while researching this, not gone looking for.** This machine reports `gpu_vendor: "amd"` throughout every Vulcan session in this workspace — but `lspci` shows only `Intel Corporation CoffeeLake-H GT2 [UHD Graphics 630]`, no AMD hardware at all, and `rocm-smi --showmeminfo vram` fails with `Driver not initialized (amdgpu not found in modules)`. Confirmed the cause by reading Vulcan's `installer/detect.py`: `detect_gpu()` does `if shutil.which("rocm-smi"): return "amd"` — a **binary-presence check, not a functional one**. `rocm-smi` happens to be installed on this machine (likely a general package, unrelated to any real AMD GPU) with no working driver behind it, and Vulcan takes that as confirmed AMD presence. Vulcan's own docstring already half-admits this ("Presence + vendor only, not driver-version validation") but the practical effect is a genuine false positive on real hardware, not just an accepted limitation. **This is the single biggest design lesson for Anvil**: unlike Vulcan (where a wrong GPU vendor guess just means Jellyfin's optional hardware transcoding silently doesn't work), Anvil's entire tier model depends on a real VRAM *number* — a presence-only false positive here would mean confidently recommending a GPU-compute tier the machine cannot deliver on at all. **Anvil's detection must run the real query and check it actually succeeds (real output, zero errors), never just check whether a tool binary exists on PATH.** Not filed as a Vulcan bug report here — Vulcan's own project, Vulcan's own call whether/when to fix it; noted here because it directly shaped this decision.

**Real, verified-syntax commands per vendor** (verified against official docs; only the AMD sysfs path was checked against this real machine's filesystem — no NVIDIA/AMD/Intel Arc discrete GPU exists here to test actual output against):

- **NVIDIA**: `nvidia-smi --query-gpu=index,memory.total --format=csv,noheader,nounits` — confirmed via NVIDIA's own docs. One line per GPU by default (real multi-GPU support built in, no extra iteration needed); `-i 0,1` targets specific indices. Reports MiB.
- **AMD, sysfs (no ROCm needed) — the real primary candidate**: `/sys/class/drm/card*/device/mem_info_vram_total` (bytes), a real amdgpu kernel driver interface confirmed via kernel.org docs, and confirmed for real on this machine that it's genuinely absent for a non-AMD card (`/sys/class/drm/card1/device/` here has no `mem_info_*` files at all — `card1`'s `vendor` file reads `0x8086`, the real Intel PCI vendor ID). This needs no extra tooling beyond the driver itself being loaded — meaningfully more robust than requiring ROCm, which consumer/gaming AMD cards frequently don't have installed even when the GPU itself is real and working.
- **AMD, ROCm (richer data if present)**: `rocm-smi --showmeminfo vram --json` — real flag confirmed via `rocm-smi --help` on this machine (JSON/CSV output both supported), but never seen real output since no AMD driver is loaded here to query.
- **Intel, discrete Arc only**: `xpu-smi discovery -d 0 -j` (Intel's own official tool, confirmed via the real `intel/xpumanager` repo) — reports `Memory Physical Size`. **Confirmed explicitly discrete-only** — Arc/Data Center GPUs, not integrated UHD/Iris.
- **Intel integrated graphics (UHD/Iris — what this machine actually has) has no equivalent at all, and that's not a gap to fill.** Integrated Intel graphics uses Unified Memory Architecture — shared system RAM, not a fixed dedicated VRAM pool the way every discrete GPU above has. There's no real "VRAM total" number to query because the concept doesn't apply the same way. **Real scoping decision, not deferred**: a host with only integrated graphics (Intel UHD/Iris, or a weak AMD APU with no real dedicated VRAM) doesn't qualify for any Anvil GPU-compute tier at all — sized-for-GPU-VRAM workloads like a 7B-parameter LLM need dedicated VRAM in the 8GB+ range, and shared system RAM contending with the OS and every other process isn't a credible substitute. This machine itself (Intel iGPU only) would correctly get no tier under this policy.
- **Multi-GPU policy, decided not deferred**: size for the **largest single card's VRAM**, not the sum — a model has to fit in one GPU's memory to run without multi-GPU-aware sharding (a much bigger, separate problem most of the candidate services don't handle out of the box), so summing would recommend tiers the host can't actually satisfy for a single model load.

The real risk - a pre-existing native Ollama install redownloading everything into a container - is now surfaced via honest port-conflict detection rather than solved via directory-sharing, which was investigated and rejected for a real, verified reason (the native store is locked to a dedicated system user, mode `0700`). - **Anvil has no interactive port-conflict resolution, unlike Vulcan's `_resolve_port_conflicts()`/"Clean Up & Retry".** Found live while verifying v0.9 (below): a pre-existing native Ollama install on `msi-laptop` (port 11434, from that same host's earlier `oracle` GPU-migration work, unrelated to Anvil) made the generated Medium-tier stack fail to start. - **RAG/voice/n8n (qdrant/embeddings/whisper/tts/n8n, v0.13) are unreachable on a fully GPU-less host, even though none of them need a GPU at all.** Both `cli.py`'s `run_install()` and `menu.sh`'s `guided_setup()` exit immediately whenever `recommend_tier()` returns no tier, which is every host `detect_system()` finds zero dedicated VRAM on. - **RAG/voice/n8n (v0.13) have no real Docker verification at all - not even `docker compose config` syntax validation, let alone a real container start.** Every prior service in this project got at least `docker compose config` validation, and most got a real container start; this slice was built in an environment with no Docker installed, so neither happened. The image tags/env vars are sourced from Osmantic/ODS's own already-running production configs (not guessed), which is real secondhand confidence - but this project's own established bar (real infrastructure verification, not just believing a rendered template) hasn't been met yet for these five services.
