# Roadmap

See [CLAUDE.md](CLAUDE.md) for the real architecture, research, and verification detail behind each item — this file is the scannable checklist version.

## Shipped

- [x] **v0.1 — first real build.** Real Python package (`installer/detect.py`/`tiers.py`/`generate.py`/`cli.py`, `templates/docker-compose.yml.j2`), following Vulcan's engine/CLI split. Service pairing (Ollama + Open WebUI, ComfyUI wired in via Open WebUI's own admin-panel setting) and VRAM tier thresholds (8GB/12GB) researched from real, current community sources rather than a placeholder list. NVIDIA-only ComfyUI at Heavy tier (`mmartial/comfyui-nvidia-docker`) to start.
- [x] **v0.1 real bugs found and fixed** — `python -m installer.cli` silently doing nothing (missing `if __name__ == "__main__": app()` guard), `comfyui_default` defaulting `True` regardless of GPU vendor in non-interactive mode, test pollution from a stray real `stack/.anvil-state.json`.
- [x] **v0.1 verification** — real `docker compose config` validation of a generated Heavy-tier NVIDIA stack; real Ollama + Open WebUI containers started on a scratch network with a real container-to-container API round trip (ComfyUI itself unverified — no NVIDIA hardware in this environment, see Next).
- [x] **v0.2 — full TUI.** `WelcomeScreen` → `ConfigScreen` → `ReviewScreen`, mirroring Vulcan's TUI shape. Bare `anvil` invocation launches the TUI by default, `--plain`/`--non-interactive` for the scriptable path. Verified for real via a `Pilot`-driven script walking a live app through all three screens with a real (detected) NVIDIA GPU.
- [x] **v0.2 — NVIDIA Container Toolkit warning.** A host can pass `nvidia-smi` detection while still lacking the separate OCI runtime hook Docker needs for GPU passthrough; `write_stack()` now warns explicitly (real install-guide URL). Deliberately no AMD/Intel equivalent — their detection only ever succeeds when the real kernel driver is already loaded, so warning to "install a driver" already-confirmed present would be actively wrong.
- [x] **v0.3 — real AMD ComfyUI support** via `corundex/comfyui-rocm` (targets consumer RX 6000/7000+ cards, the right scope for this project — not AMD's own data-center-focused official path). `vendor_restrictions` generalized from a single string to a `frozenset` to support this.
- [x] **v0.4 — real Intel Arc ComfyUI support**, closing the last vendor gap, via `yanwk/comfyui-boot:xpu` (part of the same multi-vendor project that supplied the AMD image). Root-running image, no PUID/PGID handling, needs only `/dev/dri` (no `/dev/kfd`, no `group_add`).
- [x] **v0.5 — real port-conflict detection**, replacing an assumed "shared model directory" design. Investigated for real and found Ollama/ComfyUI never share a downloadable file (different formats/domains) — the real risk is a pre-existing native Ollama install colliding on port 11434, confirmed on this project's own dev machine (a genuine running `ollama.service` with a real 4.9GB model already downloaded). Directory-sharing was considered and rejected for a verified reason (the native store is locked to a dedicated system user, mode `0700`). Shipped a real `port_in_use()` TCP probe feeding the existing warnings mechanism instead.
- [x] **v0.6 — real model-capability verification**, correcting an unverified tier claim. Verified the "8GB+ comfortable up to ~14B models" claim against Ollama's own published Q4_K_M download sizes (Llama 3.1 8B = 4.9GB, Qwen2.5 14B = 9.0GB) and cross-checked SDXL/ComfyUI guidance. The 8GB/12GB thresholds held up; the "comfortable to 14B" claim for Medium tier didn't — that comfort level genuinely belongs at Heavy. Added a `capability_note` per tier, now shown in the CLI review, TUI review summary, and as real tooltips on the tier picker (which previously showed bare unlabeled radio buttons).
- [x] **GitHub repo metadata + README landing-page pass** — About description and topics filled in (previously both empty), a scannable What/Who/Why/Where/When block added to the top of the README, a License section added pointing at the previously-unreferenced `LICENSE` file.

## Next

- [ ] **ComfyUI has never run against real NVIDIA, AMD, or Intel Arc hardware.** All three images are confirmed real and published, all three compose blocks are confirmed syntactically valid via `docker compose config` — but no discrete GPU of any vendor exists in this project's environment to actually start one against. The single biggest remaining gap.
- [ ] **No real model *load* verified against real hardware** — inference speed, real peak VRAM under load including KV-cache growth over a long context. The v0.6 tier-capability numbers are grounded in real published download sizes, not a real running model; same "no discrete GPU available" limitation as ComfyUI above.
- [ ] **CUDA/ROCm/Intel driver toolkit installation itself isn't automated.** `generate.py` warns when it's needed (real install-guide links for NVIDIA/AMD), but nothing installs or verifies the toolkit/driver is actually present — a host missing it gets a stack that fails to start, not a gracefully degraded one (unlike Vulcan, where this is optional). Larger, riskier scope than anything shipped so far; likely stays deferred, matching Vulcan's own precedent of not automating driver installs.
- [ ] **Naming.** "Anvil" is a working title picked for the Vulcan-forge/anvil pairing, not a final decision — needs a real call, not more research.
- [ ] **A second image-generation option beyond ComfyUI** — e.g. a more turnkey alternative for users who find ComfyUI's node-based UI too involved. Not scoped or researched yet.

## Deliberately out of scope

Recorded so these don't get relitigated as gaps later — each was considered and rejected for a real, documented reason.

- **Docker install/setup automation.** Vulcan has a whole `docker_setup.py` for detecting-and-installing Docker across distros; Anvil deliberately just checks readiness and points at `docs.docker.com` if it's missing. Most people reaching for GPU-compute self-hosting already have Docker — a scoped-down decision, not an oversight.
- **Sharing a model directory between a native Ollama install and this stack's container.** Investigated for v0.5 and rejected: the native store is locked to a dedicated system user (mode `0700`), and running two independent Ollama servers against the same blob store risks concurrent-write corruption regardless. Honest port-conflict detection was shipped instead.
- **Cross-tool model dedup between Ollama and ComfyUI.** They never share a downloadable file — GGUF blob-store LLMs vs. safetensors diffusion checkpoints are different formats for different domains. There was never a real problem here to solve.
