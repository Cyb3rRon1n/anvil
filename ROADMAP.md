- [x] **v0.7 — landing page + AMD ComfyUI-Manager warning.** A lightweight generated dashboard (`nginx:alpine` + a single templated `index.html`, not a full Homepage-style app) at `http://<host>:8080`, linking to whatever's actually enabled — using a real LAN-facing IP (`detect_host_ip()`, ported from Vulcan) so it works from another device, not just `localhost`. - [x] **v0.8 — InvokeAI, a second image-generation option.** Researched real, current (2026) alternatives to ComfyUI for users who find its node-based UI too involved — A1111 and the original Forge are both effectively stalled (last major releases 2024, maintainers inactive), Fooocus is LTS/bug-fixes-only with no official multi-vendor Docker story. A 4th `ServiceDefinition` at Heavy tier, `vendor_restrictions={"nvidia", "amd"}`. **A genuinely different AMD mechanism, not a copy of Ollama/ComfyUI's**: InvokeAI's AMD image needs `runtime: amd` (AMD's own separately-registered Container Toolkit runtime) instead of the plain `/dev/kfd`+`/dev/dri` passthrough this project's existing AMD blocks use — a new warning (mirroring the existing NVIDIA Container Toolkit one) tells AMD users they need it. Also genuinely simpler for the user than ComfyUI: InvokeAI has its own built-in Model Manager that downloads checkpoints directly (HuggingFace repo IDs, curated starter models) — no manual file placement, no "where do I put this" warning needed the way ComfyUI's config screen has one. **Verified past what `docker compose config` alone would show**: pulled the real NVIDIA-tag image and started a real container with no GPU (this environment has none) — it correctly fell back to CPU, ran its real DB migrations, bound its web server, and answered a real `curl` with `200`; confirmed its data volume was owned by the real passed-in `CONTAINER_UID`, not root. Separately confirmed the AMD path's honest failure mode for real: `docker run --runtime=amd` against this machine (which has no AMD Container Toolkit registered) fails with exactly `unknown or invalid runtime name: amd` — the precise scenario the new warning describes, not a hypothetical.
- [x] **v0.9 — Docker install-assist, including a real atomic/immutable-OS path — built and fully live-verified end to end against the real host that exposed the gap.** Direct fallout of trying Anvil for real against a real GPU host: `msi-laptop`, a Bazzite (Fedora Kinoite-based, rpm-ostree/atomic) laptop with a real RTX 2080, reached over Tailscale. It had no Docker and no `dnf install` path to get it — Anvil just printed a link and exited, the exact gap "Deliberately out of scope" used to name (removed from that section now that it's built). `installer/docker_setup.py` is now real (ported from Vulcan's own module of the same name: `install_plan_for`/`install_docker`/`ensure_compose_v2`/`add_user_to_docker_group`/`start_docker_service`/`run_docker_command`, same `shell.py` helpers), wired into both the CLI (`_ensure_docker_ready()`) and the TUI (`DockerReadyScreen`, inserted between `WelcomeScreen` and `ConfigScreen`) — each of the three real readiness gaps (not installed / not running / no compose v2) now gets a real confirm-then-fix step instead of a dead end. **New capability beyond what Vulcan's own version has**: `detect.py` gained `os_is_atomic` (`/run/ostree-booted` marker, confirmed for real against the actual Bazzite host — present there, absent on this project's own normal-Fedora dev machine), and `install_plan_for` checks it *before* `os_id` — a Bazzite/Kinoite host reports `os_id="fedora"` (`ID_LIKE=fedora`), which would otherwise wrongly route through the plain `get.docker.com` script against a read-only base image. The atomic path instead adds Docker's real repo file and runs `rpm-ostree install docker-ce docker-ce-cli containerd.io docker-compose-plugin docker-buildx-plugin` — layered, not live, so a successful install reports `needs_reboot: True` and both front ends stop cleanly with real reboot instructions rather than pretending Docker is ready. `group_just_added` (mirroring Vulcan's identical mechanism) threads through to the final `docker compose up` so a Docker group added in the same run doesn't need a fresh login first (`sg docker -c "..."` instead of a stale cached group list).
  - **Two real bugs found only by running this live against `msi-laptop`, neither visible from tests or reasoning about the code alone — both fixed and re-verified live:**
    1. **`detect_disk()`'s default path (`/`) is wrong on atomic hosts.** Bazzite's `/` is a tiny, nearly-full composefs snapshot (real free space ~0GB); the actual `stack/` directory Anvil writes to lives wherever it's run from - typically hundreds of GB free. Fixed by defaulting `detect_system()`'s `disk_path` to `"."` instead of `"/"` - correct on every host, atomic or not, since it's the one directory this project's own writes are guaranteed to land under. Re-verified live: `818.75GB`, not `0.0GB`.
    2. **`usermod -aG docker <user>` reports real success (exit 0) and silently writes nothing, when the `docker` group's canonical record was created by `systemd-sysusers` for a layered package and lives only in `/usr/lib/group`** (resolved via `nsswitch.conf`'s `altfiles` NSS source, never present in `/etc/group` at all) - confirmed live: `getent group docker`/`id sentinel` showed no membership change after a "successful" `usermod`, and `gpasswd -a` failed the same way, more honestly (`group 'docker' does not exist in /etc/group` - it only ever looks at the literal file, never the merged NSS view). **The real, verified fix**: a local `/etc/group` entry with the same name+gid merges cleanly with the vendor-owned entry (`nsswitch.conf`'s own `group: files [SUCCESS=merge] altfiles ...`), after which `gpasswd` manages membership on it normally - `add_user_to_docker_group()` now tries the plain `usermod` path first (works on every non-atomic host, unchanged from Vulcan's own version) and only falls back to the merge-entry trick when a real functional check (`id -nG <user>`, never trusted from a tool's own claimed exit code) shows the plain path didn't actually work. Not gated behind `os_is_atomic` - the underlying cause is what matters, not the OS family name. Confirmed live end to end: real `docker:x:958:sentinel` entry created, `id sentinel` showed real `docker` group membership afterward, and a real `sg docker -c "docker info"` succeeded where it had failed before.
  - **Verified for real, fully, not honestly-bounded-but-incomplete anymore**: ran the complete flow against `msi-laptop` end to end - fresh `rpm-ostree install` (real repo add, real 7-package layer, correct `needs_reboot` exit), a real reboot, a second run correctly detecting Docker installed-but-not-running, the real `usermod`/`gpasswd` bug hit and fixed live, a third run reaching `Docker is ready.` for real, then real tier selection (Medium, 8GB VRAM), real stack generation, and a real `docker compose up` attempt that pulled real images and started real containers - it stopped only on a pre-existing, correctly-diagnosed, out-of-scope issue (port 11434 already bound by a native Ollama install from this same host's earlier, unrelated `oracle` GPU-migration work; Anvil's own v0.5 port-conflict warning named the exact cause before the attempt, matching its documented behavior - Anvil had no interactive port-remap the way Vulcan does at the time, a separate, already-known gap - closed in v0.12, below). 141 tests cover the logic, all passing both locally and re-run for real on `msi-laptop` itself: `tests/test_docker_setup.py` (ported from Vulcan's, plus new atomic-specific cases for repo-add-then-layer sequencing, `needs_reboot` correctness, and the full `usermod`-fails/`gpasswd`-fallback sequence including its own failure modes), `tests/test_cli.py`/`tests/test_tui.py` (declined/accepted/failed install at each readiness gap, the atomic reboot message, the group-workaround wiring, the group-add-failure surfacing that was silently swallowed before this bug was found).

## Deliberately out of scope

Recorded so these don't get relitigated as gaps later — each was considered and rejected for a real, documented reason.

- **CUDA/ROCm/Intel driver toolkit installation.** `generate.py` warns when it's needed (real install-guide links for NVIDIA's Container Toolkit, AMD's Container Toolkit — the latter confirmed for real to be genuinely required by InvokeAI's `runtime: amd`, see v0.8), but nothing installs or verifies the toolkit/driver is actually present — a host missing it gets a stack that fails to start, not a gracefully degraded one (unlike Vulcan, where this is optional). Decided (2026-08-07) not to build this: larger, riskier scope (detecting and installing CUDA, ROCm, and Intel's oneAPI/level-zero stack across distros) than anything shipped so far in this project, matching Vulcan's own precedent of not automating driver installs. The warnings stay; the automation doesn't.
- **Sharing a model directory between a native Ollama install and this stack's container.** Investigated for v0.5 and rejected: the native store is locked to a dedicated system user (mode `0700`), and running two independent Ollama servers against the same blob store risks concurrent-write corruption regardless. Honest port-conflict detection was shipped instead.
- **Cross-tool model dedup between Ollama and ComfyUI.** They never share a downloadable file — GGUF blob-store LLMs vs. safetensors diffusion checkpoints are different formats for different domains. There was never a real problem here to solve.
